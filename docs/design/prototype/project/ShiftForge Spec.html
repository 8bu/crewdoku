Section 01

Product overview

ShiftForge uses a CP-SAT constraint solver to generate schedules from hard and soft constraints. Users do not draw schedules by hand. They define constraints, seed (pin) known assignments, trigger generation, and negotiate with the proposed result through a structured diff/approval flow.

This document covers the information architecture, component system, and detailed interaction specs for the four core surfaces.

Key mental model: the schedule is a generated artifact, not a spreadsheet. Every manual override and every approved request is recorded and reflected in subsequent solver runs. The solver always explains its decisions through constraint violation feedback and fairness scoring.

Surface specifications

4.1 Schedule board (Leader)

The primary leader surface. A grid matrix — employees as sticky rows, days as columns, assignments as colored cells. The solver result appears as an overlay diff on this same surface.

UI regionContents
ToolbarWeek navigation (◀ ▶ Today), zoom toggle (Week / 4-week), department filter, Seed mode toggle, Legend popover
Legend stripAlways-visible bar: shift chips (code + name + hours) + status key (pinned / pending / proposed / violation)
Seed-mode hintAppears when seed mode is on. Blue banner: click to pin/unpin; Esc to exit
Diff bannerAppears after solver returns a proposal: change count, fairness delta, accept-all / reject-all / apply / discard actions
Grid header rowSticky. Each column: DOW label + large date number + coverage chips (N/E/M/A/L counts; red if below required)
Department group rowsCollapsible. Sticky label shows dept name + headcount. Click to collapse/expand.
Employee rowsSticky name column (name + weekly hours). Day cells: shift assignment or empty.

Board interactions

  • Click cell (normal mode) → Assign popover: pick shift or clear. Shows real-time violation badges next to each option.
  • Click cell (seed mode) → Toggle pin on that cell. Only works on assigned cells.
  • Click cell (diff mode, proposed) → Diff popover: accept / reject this change.
  • Drag cell → target cell → Move assignment. Instant violation feedback on source + target.
  • Hover any cell → Tooltip: name, date, shift, pin status, pending request, violations, proposed change.

On approve: the assignment override is immediately applied to the board. If the ripple pre-check was "warn" or "crit", the leader can still approve — but the system shows the warning. No hard blocks on approval; the leader is always in control.

5.3 Manual override with live violation feedback

  1. Leader clicks an assigned cell on the board → Assign popover opens.
  2. Each shift option shows a ⚠ badge if assigning it would break H3 (rest), H2 (hours), or H1 (coverage). Badge is a tooltip with the exact rule ID and reason.
  3. Leader picks a shift (may choose a violating one). Cell immediately shows .sf-viol style (red outline + ⚠).
  4. Status bar at the bottom increments violation count.
  5. The violation is carried into the next generation run as context; the solver may or may not be able to fix it depending on other constraints.
Manual overrides are advisory violations only — the app never blocks an action. This is intentional: leaders must be able to handle emergency situations that the solver cannot anticipate.

5.4 Swap consent flow

  1. Member A submits a swap request with Member B.
  2. Member B sees a consent prompt in their Requests view.
  3. Until B accepts: request shows CONSENT AWAITING badge; Approve button is disabled in leader inbox.
  4. Once B accepts: request becomes actionable. Leader sees it with consent ✓.
  5. If leader approves: both cells update simultaneously (A gets B's shift, B gets A's shift).

Section 09

Technical architecture notes

State management

Single useReducer at the root App component. All surfaces receive app (state) and dispatch as props. No context, no external state library. The state shape is flat and serializable (except Set and Map for pins/overrides/decided).

Solver simulation

The prototype simulates the solver deterministically using a seeded pseudo-random function. Key behaviors that are computed for real (not faked): rest-window violations (H3), weekly hours cap (H2), coverage drop from overrides (H1). These give genuine red cells and violation tooltips when you drag assignments.

Performance

The board renders 100 rows × 7–28 columns = 700–2,800 cells. Each Row is wrapped in React.memo. Hover tooltips use an imperative ref layer (TooltipLayer) so mouse events never trigger React re-renders. Coverage chips are memoized separately.
